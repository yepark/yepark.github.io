# PKCS #12: 인증서와 개인 키를 옮기는 .p12/.pfx
{: .no_toc }

{% include article-toc.md %}

PKCS #12는 개인 키, 인증서, 인증서 체인, 기타 비밀과 속성을 한 파일로 옮기기 위한 형식이다. `.p12`와 `.pfx` 확장자로 자주 만난다. PFX(Personal Information Exchange)는 이 형식의 옛 이름이자 최상위 구조의 이름이다. iOS 개발에서 푸시 인증서나 배포 인증서를 다른 Mac으로 옮길 때 내보내는 파일이 바로 이 형식이다. 핵심 문서는 **RFC 7292, PKCS #12 v1.1**이다.

## 인증서 파일과 신원 묶음의 차이

인증서는 공개 키와 주체 정보를 담고, 개인 키는 소유자만 보관해야 하는 비밀이다. PKCS #12는 이 둘과 중간 인증서를 한 파일로 이동할 때 자주 사용한다.

파일을 가져오는 패스워드를 안다고 그 인증서의 발급자를 신뢰할 수 있는 것은 아니다. 패스워드 보호 확인, 개인 키와 인증서의 일치 확인, 인증서 체인 검증을 각각 수행해야 한다.

## 무엇이 들어갈까

```text
PFX
└── AuthenticatedSafe
    ├── 개인 키 또는 암호화된 개인 키
    ├── 사용자 인증서
    ├── 중간 CA 인증서
    └── 별칭·키 연결 속성
```

하나의 PFX에 여러 키와 인증서가 들어갈 수도 있다. 파일 확장자만 보고 인증서 하나라고 가정하면 안 된다.

## 최상위 PFX 구조

```asn1
PFX ::= SEQUENCE {
    version   INTEGER {v3(3)},
    authSafe  ContentInfo,
    macData   MacData OPTIONAL
}
```

- `version`: 현재 값 3
- `authSafe`: `AuthenticatedSafe`를 담고 보호하는 CMS `ContentInfo`
- `macData`: 패스워드 기반 무결성 검사 정보

## SafeBag 종류

| Bag | 내용 |
| --- | --- |
| `keyBag` | 암호화되지 않은 PKCS #8 개인 키 |
| `pkcs8ShroudedKeyBag` | 패스워드로 암호화된 PKCS #8 개인 키 |
| `certBag` | X.509 인증서 등 |
| `crlBag` | 인증서 폐지 목록 |
| `secretBag` | 기타 비밀 |
| `safeContentsBag` | SafeBag을 다시 중첩 |

`friendlyName`은 사람이 보는 별칭이고 `localKeyId`는 개인 키와 인증서를 연결하는 데 사용된다. 실제 키 쌍 일치는 공개 키를 비교해 확인해야 한다.

## 암호화와 무결성은 다르다

- 암호화: 파일을 본 사람이 개인 키 내용을 읽지 못하게 함
- MAC: 패스워드를 모르는 사람이 파일을 변조했는지 확인

둘 중 하나만 있다고 둘 다 해결되는 것이 아니다. 빈 패스워드와 MAC 생략도 구현체마다 처리 차이가 있어 상호 운용 테스트가 필요하다.

## 패스워드 처리 주의

기존 PKCS #12는 고유한 패스워드 인코딩과 KDF를 사용해 라이브러리 간 빈 문자열·NULL 처리에서 차이가 발생해 왔다. 직접 문자열을 바이트로 바꾸지 말고 사용하는 라이브러리의 PKCS #12 API를 사용한다.

RFC 9879는 RFC 7292와 RFC 8018을 보완(`Updates`)하고 PBMAC1을 PKCS #12 무결성 보호에 사용할 방법을 정의해 PBKDF2나 scrypt 같은 확장 가능한 KDF 사용을 허용하고, RFC 9579를 폐기한다. 다만 새 방식의 실제 지원 여부는 운영체제와 라이브러리마다 확인해야 한다.

## OpenSSL로 내용 확인하기

개인 키를 출력하지 않고 인증서와 메타데이터를 먼저 확인한다.

```bash
openssl pkcs12 -in identity.p12 -info -nokeys
```

개인 키를 평문 파일로 내보내는 명령은 터미널 기록, 파일 권한, 백업에 키를 노출할 수 있다. 꼭 필요하지 않으면 하지 않는다.

## 가져올 때 검증할 항목

1. MAC과 암호 해제가 성공했는가
2. 허용한 알고리즘과 파라미터인가
3. 개인 키와 리프 인증서(체인의 맨 끝에 있는, 실제 서버나 사용자의 인증서)의 공개 키가 일치하는가
4. 인증서 체인의 서명과 순서가 유효한가
5. 예상하지 못한 추가 키·인증서·secret bag이 없는가
6. 가져온 개인 키를 안전한 키 저장소로 이동했는가

PFX 파일의 MAC이 맞는다는 사실은 인증서 발급자를 신뢰한다는 뜻이 아니다. 인증서 체인, 이름, 용도, 기간, 폐지 상태는 사용 시점에 별도로 검증한다.

## 암호를 풀었는데도 신원 사용을 거부해야 하는 경우

PFX의 패스워드가 맞고 내부 키를 읽을 수 있어도 다음 경우에는 의도한 신원으로 사용하면 안 된다. 인증서와 키가 짝이 아니거나, 인증서가 만료됐거나, 예상한 발급자와 용도가 아니거나, 허용하지 않은 추가 신원이 함께 들어 있을 수 있다.

예를 들어 표시 이름이 `company-server`인 항목 두 개가 있다면 이름만으로 하나를 고르지 않는다. 공개 키 일치 여부와 인증서의 주체·용도, 가져오기 정책으로 선택한다. 별칭은 사람이 보는 정보이고 암호학적 식별이나 신뢰의 대체물이 아니다.

## 중첩 구조를 순서대로 읽기

```text
PFX
  → authSafe의 ContentInfo
  → AuthenticatedSafe: ContentInfo들의 묶음
  → 각 항목의 보호를 해제해 SafeContents 확인
  → SafeBag들의 키·인증서·속성 해석
```

[RFC 7292 §4](https://www.rfc-editor.org/rfc/rfc7292.html#section-4)의 구조를 위 순서로 따라가고, §5의 생성·가져오기 절차와 연결한다. 개인 키 bag 자체의 보호와 그 bag을 담은 safe의 보호는 서로 다른 층일 수 있다. 파일 전체를 한 번 복호화하면 모든 검증이 끝난다고 생각하면 내부 항목의 보호와 정책을 놓치기 쉽다.
