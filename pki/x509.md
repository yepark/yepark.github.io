# X.509 인증서 구조와 검증
{: .no_toc }

{% include article-toc.md %}

HTTPS 사이트에 접속하면 서버는 "나는 api.example.com이고, 내 공개 키는 이것이다"라는 문서를 보낸다. 이 문서가 **인증서**다. 아무나 이런 문서를 만들 수 있으므로, 인증서에는 그 내용을 보증한 **인증기관(CA)의 전자서명**이 붙어 있다. 인터넷에서 쓰는 인증서 형식이 **X.509**이고, 현재 버전은 v3다.

이 글에서는 OpenSSL로 학습용 루트 CA와 서버 인증서를 직접 만들어 구조를 뜯어보고, 검증이 어떤 경우에 실패하는지 실제 오류로 확인한다. 실행 환경은 OpenSSL 3.0.13이다.

## 인증서 만들기

```bash
# 1) 루트 CA: 자기 자신이 서명한 인증서
openssl req -x509 -newkey ec -pkeyopt ec_paramgen_curve:P-256 -nodes \
  -keyout ca.key -out ca.pem -days 365 -subj "/C=KR/O=Example Lab/CN=Example Lab Root CA" \
  -addext "basicConstraints=critical,CA:TRUE" -addext "keyUsage=critical,keyCertSign,cRLSign"

# 2) 서버: 키를 만들고 인증서 서명 요청(CSR)을 작성
openssl req -newkey ec -pkeyopt ec_paramgen_curve:P-256 -nodes \
  -keyout leaf.key -out leaf.csr -subj "/C=KR/O=Example Lab/CN=api.example.test"

# 3) CA가 CSR에 서명해 서버 인증서 발급 (확장은 leaf.ext 파일로)
openssl x509 -req -in leaf.csr -CA ca.pem -CAkey ca.key -CAcreateserial \
  -out leaf.pem -days 90 -extfile leaf.ext
```

`leaf.ext`에는 서버 인증서에 넣을 확장을 적었다.

```text
basicConstraints = critical, CA:FALSE
keyUsage = critical, digitalSignature
extendedKeyUsage = serverAuth
subjectAltName = DNS:api.example.test, DNS:www.example.test
```

이 흐름이 실제 CA의 발급 과정과 같다. 서버는 개인 키를 밖으로 보내지 않고 공개 키가 든 [CSR(PKCS #10)]({{ '/pki/pkcs10/' | relative_url }})만 보내며, CA는 신원을 확인한 뒤 자신의 개인 키로 서명한 인증서를 돌려준다.

## 인증서 안을 들여다보기

```bash
openssl x509 -in leaf.pem -noout -text
```

```text
Certificate:
    Data:
        Version: 3 (0x2)
        Serial Number: ...
        Signature Algorithm: ecdsa-with-SHA256
        Issuer: C = KR, O = Example Lab, CN = Example Lab Root CA
        Validity
            Not Before: Nov 27 11:49:15 2026 GMT
            Not After : Feb 25 11:49:15 2027 GMT
        Subject: C = KR, O = Example Lab, CN = api.example.test
        Subject Public Key Info:
            Public Key Algorithm: id-ecPublicKey
                Public-Key: (256 bit)
                NIST CURVE: P-256
        X509v3 extensions:
            X509v3 Basic Constraints: critical
                CA:FALSE
            X509v3 Key Usage: critical
                Digital Signature
            X509v3 Extended Key Usage:
                TLS Web Server Authentication
            X509v3 Subject Alternative Name:
                DNS:api.example.test, DNS:www.example.test
            X509v3 Subject Key Identifier: F5:00:63:...
            X509v3 Authority Key Identifier: FC:FC:F9:...
    Signature Algorithm: ecdsa-with-SHA256
    Signature Value: ...
```

인증서는 크게 세 부분이다.

```text
┌ tbsCertificate (서명 대상 본문) ┐
│  버전, 일련번호, 발급자, 유효 기간,  │
│  주체, 주체 공개 키, 확장          │
├ signatureAlgorithm ─────────────┤
├ signatureValue (CA의 서명) ──────┘
```

| 필드 | 뜻 |
| --- | --- |
| Serial Number | CA가 붙인 일련번호. 폐지 목록에서 이 번호로 찾는다 |
| Issuer | 서명한 CA의 이름 |
| Validity | 유효 기간. 서버 인증서는 점점 짧아지는 추세다 |
| Subject | 인증서 주인의 이름([DN]({{ '/pki/pkcs10-subject/' | relative_url }})) |
| Subject Public Key Info | 주인의 공개 키와 알고리즘([SPKI]({{ '/pki/ssl-pinning/' | relative_url }}), 피닝 값을 계산하는 부분) |
| Extensions | 용도와 제약 ([PKCS #6]({{ '/pki/pkcs6/' | relative_url }}) 글의 확장 표) |
| Signature | 본문 전체에 대한 CA의 서명 |

### 이름은 Subject가 아니라 SAN에서

서버 이름을 확인할 때는 Subject의 CN이 아니라 **Subject Alternative Name(SAN)** 확장을 본다. 브라우저와 iOS는 CN을 서버 이름 확인에 쓰지 않는다. 인증서 하나에 여러 이름(`api`, `www`)을 넣을 수 있는 것도 SAN 덕분이다.

### 체인을 잇는 키 식별자

서버 인증서의 **Authority Key Identifier**는 서명한 CA 공개 키의 식별자이고, CA 인증서의 **Subject Key Identifier**와 같다. 검증 프로그램은 이 값으로 "이 인증서에 서명한 CA 인증서"를 찾아 체인을 위로 이어 간다.

## 검증: 무엇을 확인하나

```bash
openssl verify -CAfile ca.pem -verify_hostname api.example.test leaf.pem
```

```text
leaf.pem: OK
```

이 한 줄이 통과하려면 다음이 모두 맞아야 한다.

1. 서버 인증서의 서명을 발급자(CA)의 공개 키로 검증한다.
2. 발급자를 따라 올라가 **신뢰 앵커**(내가 미리 믿기로 한 루트 인증서)에 닿는다.
3. 체인의 모든 인증서가 유효 기간 안이다.
4. 중간에 있는 인증서는 CA 권한(Basic Constraints `CA:TRUE`)과 서명 용도가 있다.
5. 서버 인증서의 용도(Extended Key Usage)가 지금 목적(서버 인증)과 맞다.
6. 접속한 이름이 SAN에 있다.
7. (실제 환경에서는) 폐지되지 않았다(CRL·OCSP).

## 실패하는 다섯 가지 경우

같은 인증서로 조건을 하나씩 어긋나게 해 실행했다.

| 경우 | 명령 | 결과 |
| --- | --- | --- |
| 신뢰 앵커 없음 | `openssl verify leaf.pem` | `error 20: unable to get local issuer certificate` |
| 이름 불일치 | `-verify_hostname evil.example.test` | `error 62: hostname mismatch` |
| 용도 불일치 | `-purpose sslclient` | `error 26: unsuitable certificate purpose` |
| 만료 | `-attime` 200일 뒤 | `error 10: certificate has expired` |
| 변조 | 본문의 이름 1바이트 변경 | 서명 검증 실패 (`ASN1_item_verify_ctx`) |

- **신뢰 앵커 없음**: 서명이 멀쩡해도, 루트 CA를 신뢰 저장소에 넣지 않으면 실패한다. 사설 CA로 만든 인증서를 iPhone이 믿지 않는 이유다. 사설 CA를 믿게 하려면 MDM의 [구성 프로파일]({{ '/ios/mdm/profiles/' | relative_url }})로 루트 인증서를 배포한다.
- **이름 불일치**: 공격자가 정상 CA에서 `evil.example.test` 인증서를 받아도 `api.example.test`로는 쓸 수 없다.
- **용도 불일치**: 서버 인증용(`serverAuth`)으로만 발급된 인증서는 클라이언트 인증에 쓸 수 없다.
- **만료**: 기기 시계가 틀려도 같은 오류가 난다.
- **변조**: 본문의 `api`를 `xpi`로 1바이트만 바꿨는데 CA의 서명이 더 이상 맞지 않았다. 인증서 내용은 CA의 서명 없이 바꿀 수 없다.

## 실제 인터넷의 체인

실제 서버 인증서는 루트 CA가 직접 서명하지 않는다. 루트 CA의 개인 키는 오프라인 금고에 보관하고, 루트가 서명한 **중간 CA**가 서버 인증서를 발급한다.

```text
[루트 CA]  ← 기기의 신뢰 저장소에 들어 있음, 서버가 보내지 않아도 됨
   ↓ 서명
[중간 CA]  ← 서버가 함께 보내야 함
   ↓ 서명
[서버 인증서]
```

서버가 중간 인증서를 빠뜨리면, 일부 브라우저는 다른 경로로 찾아 성공하고 앱이나 다른 클라이언트는 `unable to get local issuer certificate`로 실패하는 일이 생긴다. "브라우저는 되는데 앱은 안 된다"면 먼저 서버가 보내는 체인을 확인한다. 실제 체인을 관찰하는 방법은 [TLS 인증서 검증과 피닝]({{ '/pki/ssl-pinning/' | relative_url }})에 있다.

## 정리

- X.509 인증서는 본문(발급자, 주체, 기간, 공개 키, 확장)과 그에 대한 CA의 서명으로 이루어진다.
- 서버 이름은 SAN으로 확인하고, Authority/Subject Key Identifier로 체인을 잇는다.
- 검증은 서명, 신뢰 앵커까지의 경로, 기간, CA 권한, 용도, 이름, 폐지 여부를 모두 본다.
- 신뢰 앵커 없음·이름·용도·만료·변조 각각에서 검증이 실패하는 것을 직접 확인했다.
