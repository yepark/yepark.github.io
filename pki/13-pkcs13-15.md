# PKCS #13·#14·#15: 발표되지 않은 번호와 스마트카드 형식
{: .no_toc }

{% include article-toc.md %}

PKCS 연재를 #12까지 읽었다면 "#13은 어디 갔지?"라는 질문이 남는다. 결론부터 말하면 **PKCS #13과 #14는 정식 규격으로 발표되지 않았다.** RSA Laboratories가 번호를 정하고 작업을 시작했지만 최종본이 나오지 않았고, 그 사이 같은 주제를 다른 표준 기구가 먼저 정리했다. #15는 발표됐고, 지금은 국제 표준 ISO/IEC 7816-15로 이어졌다.

| 번호 | 다루려던 주제 | 상태 | 지금 대신 보는 표준 |
| --- | --- | --- | --- |
| PKCS #13 | 타원곡선 암호(ECC) | 발표되지 않음 | SEC 1, ANSI X9.62, FIPS 186, RFC 5480·5915 |
| PKCS #14 | 의사난수 생성 | 발표되지 않음 | NIST SP 800-90A/B/C, RFC 4086 |
| PKCS #15 | 스마트카드 안의 키·인증서 정보 형식 | v1.1 발표 | ISO/IEC 7816-15 |

## PKCS #13: 타원곡선 암호

### 무엇을 하려던 번호였나

**타원곡선 암호(ECC, Elliptic Curve Cryptography)**는 RSA처럼 공개 키와 개인 키를 쓰지만, 큰 수의 소인수분해 대신 "타원곡선 위의 점을 몇 번 더했는지 거꾸로 알아내기 어렵다"는 문제(타원곡선 이산 로그 문제)에 안전성을 둔다. 같은 보안 수준에서 키가 훨씬 짧다. 128비트 보안 수준을 얻으려면 RSA는 3072비트 키가 필요하지만, ECC는 256비트 키면 된다.

PKCS #13은 이 ECC의 키 형식과 서명·키 합의 방식을 RSA의 PKCS #1처럼 정리하려던 번호였다. 하지만 최종 규격이 나오기 전에 다른 기구들이 같은 내용을 표준으로 만들었고, 업계는 그쪽을 따랐다.

### 지금 ECC는 어떤 표준을 보나

| 표준 | 내용 |
| --- | --- |
| SEC 1 (SECG) | 타원곡선 키 생성, ECDSA·ECDH, 개인 키 구조(`ECPrivateKey`) |
| ANSI X9.62 | 금융권용 ECDSA 규격 |
| NIST FIPS 186 | 정부용 전자서명 표준. P-256, P-384 같은 곡선과 ECDSA·EdDSA |
| RFC 5480 | 인증서 안에 EC 공개 키를 넣는 방법(`id-ecPublicKey`) |
| RFC 5915 | EC 개인 키 파일 구조(SEC 1의 `ECPrivateKey`를 IETF 문서로 정리) |
| RFC 7748, RFC 8032 | X25519·X448 키 합의, Ed25519·Ed448 서명 |

iOS의 CryptoKit이 제공하는 `P256`, `P384`, `Curve25519`가 바로 이 표준들의 곡선이다. 앱에서 "EC 키"를 다룬다면 PKCS #13이 아니라 위 문서를 찾아보면 된다.

### EC 키 파일을 직접 열어 보기

RSA 키에 PKCS #1 전용 형식과 PKCS #8 공통 형식이 있었던 것처럼, EC 키에도 두 가지 형식이 있다. OpenSSL 3.0으로 P-256 키를 만들어 구조를 확인했다.

```bash
openssl ecparam -name prime256v1 -genkey -noout -out sec1.pem
openssl pkcs8 -topk8 -nocrypt -in sec1.pem -out p8.pem
openssl ec -in sec1.pem -pubout -out pub.pem
```

`prime256v1`은 P-256 곡선의 OpenSSL 이름이다. 세 파일의 첫 줄은 이렇다.

```text
sec1.pem  -----BEGIN EC PRIVATE KEY-----
p8.pem    -----BEGIN PRIVATE KEY-----
pub.pem   -----BEGIN PUBLIC KEY-----
```

`openssl asn1parse`로 안쪽 구조를 보면 차이가 드러난다. 개인 키 값은 `...`로 가렸다.

```text
# sec1.pem: SEC 1 / RFC 5915의 ECPrivateKey (EC 전용 형식)
SEQUENCE
  INTEGER       :01                ← 버전
  OCTET STRING  [32바이트 개인 키 ...]
  cont [ 0 ]
    OBJECT      :prime256v1        ← 곡선 이름
  cont [ 1 ]
    BIT STRING                     ← 공개 키 (65바이트)

# p8.pem: PKCS #8 (알고리즘 공통 상자)
SEQUENCE
  INTEGER       :00
  SEQUENCE
    OBJECT      :id-ecPublicKey    ← "안쪽은 EC 키"
    OBJECT      :prime256v1
  OCTET STRING  [안쪽에 위의 ECPrivateKey가 들어 있음 ...]

# pub.pem: X.509 SubjectPublicKeyInfo (RFC 5480)
SEQUENCE
  SEQUENCE
    OBJECT      :id-ecPublicKey
    OBJECT      :prime256v1
  BIT STRING                       ← 공개 키
```

`BEGIN EC PRIVATE KEY`는 EC 전용 형식이고, `BEGIN PRIVATE KEY`는 [PKCS #8]({{ '/pki/pkcs8/' | relative_url }}) 상자 안에 같은 EC 키를 넣은 것이다. RSA의 `BEGIN RSA PRIVATE KEY`와 `BEGIN PRIVATE KEY`의 관계와 똑같다. 공개 키의 65바이트는 맨 앞 `04`(압축하지 않은 점이라는 표시)와 x좌표 32바이트, y좌표 32바이트로 이루어진다.

서버에서 받은 EC 키를 iOS에서 쓸 때 흔히 막히는 지점이 여기다. CryptoKit의 `P256.Signing.PrivateKey(pemRepresentation:)`은 두 형식의 PEM을 모두 읽지만, Security 프레임워크의 `SecKeyCreateWithData`는 PEM 머리글이나 ASN.1 상자 없이 정해진 원시 바이트 형식을 기대한다. "키 파일이 안 읽힌다"면 먼저 머리글과 `asn1parse` 결과로 어떤 형식인지 확인한다.

## PKCS #14: 의사난수 생성

### 무엇을 하려던 번호였나

암호에서 키, IV, salt, nonce는 모두 **예측할 수 없는 난수**여야 한다. 컴퓨터는 정해진 계산만 하므로, 실제로는 짧은 진짜 무작위 값(엔트로피, 하드웨어 잡음 등)을 씨앗으로 받아 긴 난수열을 계산으로 늘린다. 이것을 **의사난수 생성기(PRNG)**라고 하고, 암호에 써도 될 만큼 예측이 어려운 것을 **CSPRNG**(Cryptographically Secure PRNG)라고 한다.

PKCS #14는 이 의사난수 생성 방법을 표준으로 정리하려던 번호였지만 발표되지 않았다.

### 지금은 무엇을 보나

| 표준 | 내용 |
| --- | --- |
| NIST SP 800-90A | 해시·HMAC·AES 기반 난수 생성기(DRBG) 설계 |
| NIST SP 800-90B | 씨앗이 되는 엔트로피 소스 평가 |
| NIST SP 800-90C | 둘을 조합해 난수 생성기를 구성하는 방법 |
| RFC 4086 | 보안용 난수의 요구사항과 흔한 실수 |

앱 개발자가 직접 난수 생성기를 만들 일은 거의 없다. 운영체제가 제공하는 CSPRNG를 쓰면 된다.

```swift
import Security

var bytes = [UInt8](repeating: 0, count: 32)
let status = SecRandomCopyBytes(kSecRandomDefault, bytes.count, &bytes)
guard status == errSecSuccess else { fatalError("난수 생성 실패") }
```

Swift의 `SystemRandomNumberGenerator`(`Int.random(in:)` 등이 기본으로 쓰는 생성기)와 CryptoKit의 `SymmetricKey(size: .bits256)`도 운영체제의 CSPRNG를 사용한다. 피해야 할 것은 시각이나 프로세스 ID를 씨앗으로 직접 만든 난수, 재현 가능하도록 시드를 고정한 테스트용 생성기를 실제 키 생성에 쓰는 것이다.

## PKCS #15: 스마트카드 안의 키 정보 형식

### 무엇을 정의하나

스마트카드나 USB 보안 토큰에는 개인 키, 인증서, PIN 정보가 들어 있다. 그런데 카드마다 이 정보를 저장하는 파일 구조가 다르면, 프로그램은 카드 제조사마다 다른 코드를 써야 한다.

**PKCS #15(Cryptographic Token Information Format Standard)**는 "카드 안에 어떤 키와 인증서가 어디에 있는지"를 적어 두는 공통 파일 형식이다. 카드를 꽂은 프로그램은 PKCS #15 디렉터리를 읽고 "서명용 개인 키는 이 위치, 짝이 되는 인증서는 이 위치, 이 키를 쓰려면 이 PIN이 필요"라는 정보를 얻는다. 2000년에 v1.1이 발표됐고, 이후 국제 표준 **ISO/IEC 7816-15**로 이어졌다.

### PKCS #11과의 차이

두 번호는 자주 함께 나오지만 맡는 층이 다르다.

| 구분 | [PKCS #11]({{ '/pki/pkcs11/' | relative_url }}) | PKCS #15 |
| --- | --- | --- |
| 무엇인가 | 프로그램이 부르는 함수(API) | 카드 안에 저장된 정보의 형식 |
| 비유 | 은행 창구에서 쓰는 업무 절차 | 금고 안 서류의 정리 규칙 |
| 누가 쓰나 | 애플리케이션 개발자 | 카드 발급자, 미들웨어 개발자 |

실제 구성에서는 PKCS #11 모듈(미들웨어)이 카드의 PKCS #15 구조를 읽어, 애플리케이션에는 PKCS #11 함수로 키와 인증서를 보여 준다. 오픈소스 OpenSC가 이런 미들웨어의 대표 예다.

### 지금 어디서 만나나

국가 전자 신분증, 공무원 인증 카드, 기업용 출입·서명 카드처럼 인증서가 든 스마트카드에서 만난다. iOS 앱에서는 CryptoTokenKit 프레임워크가 스마트카드 접근을 담당하며, 카드의 형식을 해석하는 일은 토큰 드라이버가 맡는다. 앱 개발자가 PKCS #15 파일 구조를 직접 파싱할 일은 드물다.

## 정리

- PKCS #13(타원곡선)과 #14(의사난수)는 번호만 정해지고 정식 발표되지 않았다.
- ECC는 SEC 1, FIPS 186, RFC 5480·5915 등을 본다. EC 개인 키는 EC 전용 형식(`BEGIN EC PRIVATE KEY`)과 PKCS #8 형식(`BEGIN PRIVATE KEY`) 두 가지로 저장된다.
- 난수는 NIST SP 800-90 계열이 기준이고, 앱에서는 운영체제의 CSPRNG를 쓴다.
- PKCS #15는 스마트카드 안의 키·인증서 정보 형식이며 ISO/IEC 7816-15로 이어졌다. PKCS #11(API)과는 맡는 층이 다르다.
