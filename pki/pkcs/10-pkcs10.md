# PKCS #10: 인증서 서명 요청 CSR
{: .no_toc }

{% include article-toc.md %}

PKCS #10은 인증기관(CA)에 인증서 발급을 요청할 때 쓰는 CSR(Certificate Signing Request)의 문법을 정의한다. 현재 문서는 **RFC 2986**이다.

## 발급 절차에서 CSR의 위치

먼저 사용자가 키 쌍을 만들고 개인 키는 보호한 채 공개 키를 CSR에 넣는다. 그 CSR을 CA에 보내면 CA는 신원과 발급 정책을 확인하고 최종 인증서를 만든다.

CSR의 자체 서명은 해당 공개 키에 맞는 개인 키를 사용할 수 있었다는 증거다. 이름이나 도메인의 소유권을 자동으로 증명하지는 않는다. 요청을 검증하는 일과 최종 인증서를 신뢰하는 일을 나눠 읽자.

## CSR 구조

```asn1
CertificationRequest ::= SEQUENCE {
    certificationRequestInfo CertificationRequestInfo,
    signatureAlgorithm       AlgorithmIdentifier,
    signature                BIT STRING
}
```

안쪽 `CertificationRequestInfo`에는 다음이 들어간다.

- 버전: 현재 `0`
- Subject DN: 발급받을 주체 이름
- SubjectPublicKeyInfo: 공개 키 알고리즘과 공개 키
- Attributes: 추가 요청 정보

요청자는 이 전체 정보에 대응하는 개인 키로 서명한다.

발급기관은 먼저 CSR 안의 공개 키로 요청 서명을 검증한다. 그다음 요청된 이름과 용도가 발급 정책에 맞는지 검사한다. 통과하면 새로운 인증서 본문을 만들고 CA의 개인 키로 서명한다. CSR 서명과 최종 인증서 서명은 서명자와 대상 데이터가 다르다.

## CSR 서명이 증명하는 것

CSR 서명을 포함된 공개 키로 검증하면 요청자가 대응하는 개인 키를 보유했다는 사실을 확인할 수 있다. 하지만 다음을 자동으로 증명하지는 않는다.

- Subject 이름이 실제 사람·회사와 일치함
- 요청한 DNS 도메인을 통제함
- 요청한 용도가 정책상 허용됨
- 공개 키가 안전하게 생성·보관됨

이 검증은 CA의 신원 확인과 도메인 검증, 발급 정책이 담당한다.

## extensionRequest

PKCS #9의 `extensionRequest` 속성을 사용해 인증서에 넣고 싶은 X.509 v3 확장을 요청할 수 있다.

```text
Subject Alternative Name: example.com, www.example.com
Key Usage: Digital Signature
Extended Key Usage: TLS Web Server Authentication
```

CA는 요청을 검토하고 정책에 따라 최종 인증서 내용을 결정한다.

## PEM 표현

```text
-----BEGIN CERTIFICATE REQUEST-----
Base64로 인코딩된 DER
-----END CERTIFICATE REQUEST-----
```

PEM은 전달 표현일 뿐이며 핵심 구조는 안쪽 DER이다. CSR에는 개인 키가 들어가지 않는다.

## CA가 검증할 항목

1. ASN.1과 DER 구조가 유효한가
2. CSR 서명이 포함된 공개 키로 검증되는가
3. 키 알고리즘과 키 크기가 정책을 만족하는가
4. Subject DN과 요청 확장이 허용되는가
5. 이름과 신원 검증 절차를 통과했는가
6. 중복·알 수 없는 속성을 안전하게 처리하는가

Subject DN과 국내 프로파일은 [PKCS#10 인증서 서명 요청과 Subject DN]({{ '/pki/pkcs10-subject/' | relative_url }})에서 더 자세히 설명한다.

## 요청자 서명과 CA 서명을 그림으로 구분하기

```text
요청자의 개인 키
  └─ CSR 정보에 서명
       └─ CA가 CSR 안의 공개 키로 검증

CA의 개인 키
  └─ 발급할 인증서 본문에 서명
       └─ 사용자가 발급자 공개 키와 신뢰 정책으로 검증
```

두 서명은 대상 데이터도 서명 키도 다르다. CSR을 검증했다는 사실만으로 CA가 최종 인증서를 발급했다고 볼 수 없다. CSR 파일은 발급 요청의 입력이고, 최종 인증서는 CA가 정책에 따라 만든 별도 결과물이다.

‘요청한 DNS 이름’도 ‘검증된 DNS 이름’과 다르다. 요청자가 자기 개인 키로 서명할 수 있어도 다른 사람의 도메인 이름을 CSR에 적는 것 자체는 가능하다. CA가 그 이름에 대한 통제를 별도로 확인해야 하는 이유다.

## RFC에서 서명 대상을 찾는 방법

[RFC 2986 §4.1](https://www.rfc-editor.org/rfc/rfc2986.html#section-4.1)의 요청 정보와 §4.2의 전체 CSR을 비교한다. 서명 대상은 요청 정보의 DER 인코딩이며, 전체 CSR 바이트에 그 CSR의 서명을 다시 포함해 서명하는 구조가 아니다.

검증할 때는 임의로 문자열을 정리하거나 DN 항목 순서를 바꾼 뒤 확인하지 않는다. 사람이 보기 같은 이름이라고 해서 바이트 표현까지 같은 것은 아니다. ASN.1 라이브러리와 CSR 전용 API를 사용하고, 요청 확장을 최종 인증서로 무조건 복사하지 않는다.
