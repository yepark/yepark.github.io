# MLX 지연 평가와 성능 측정
{: .no_toc }

{% include article-toc.md %}

MLX의 연산 시간은 Python에서 연산식을 작성한 줄의 실행 시간과 일치하지 않는다. 지연 평가에서는 계산 관계를 구성한 뒤 실제 값이 필요한 시점에 실행하기 때문이다. GPU에서는 작업을 제출하는 시점과 완료하는 시점도 구분된다.

**지연 평가(lazy evaluation)**는 연산식을 만나는 즉시 계산하지 않고, 어떤 값을 어떻게 계산할지만 기록해 두었다가 결과가 실제로 필요할 때 계산하는 실행 방식이다. MLX에서는 `mx.eval`을 호출하거나, 값을 출력하거나, NumPy 배열로 바꾸는 시점에 계산이 일어난다.

이 글에서는 계산 그래프, 평가와 동기화, 캐시된 결과를 구분한다. 이어서 직접 실행한 작은 벤치마크를 해석하고, 어떤 결론까지 정당화할 수 있는지 살펴본다.

## 세 가지 시점: 구성, 제출, 완료

```python
c = a @ b
mx.eval(c)
```

첫 줄은 행렬곱 결과를 표현하는 배열 노드를 만든다. 두 번째 줄은 결과를 평가하고, 호출자가 사용할 수 있도록 완료를 기다린다.

실행 모델은 다음처럼 나눠 볼 수 있다.

```text
그래프 구성 → 의존 입력 평가와 작업 예약 → 장치 실행 → 완료 대기 해제
```

서로 다른 함수가 담당하더라도 이 단계 사이의 순서는 연산 의존성을 지켜야 한다. 다른 스트림의 작업이나 이미 예약된 입력이 있으면 대기 관계가 추가될 수 있다.

### 내부 상태 이름을 그대로 해석하지 않기

분석한 소스의 `array::Status`에는 `unscheduled`, `evaluated`, `available`이 있다. 특히 `evaluated`는 평가 함수가 실행됐음을 나타내지만 장치 계산이 반드시 끝났다는 뜻은 아니다. 버퍼가 있어도 작업이 진행 중일 수 있다.

이 구분은 [array.h의 상태 설명](https://github.com/ml-explore/mlx/blob/fc344c986c4169d99f76b5d95ae6b4a58a359a63/mlx/array.h#L376)에서 확인할 수 있다. 애플리케이션에서는 이런 내부 enum에 의존하지 않고 공개 평가·동기화 API를 사용한다.

## 평가를 유발하는 관찰

배열을 Python 값으로 꺼내거나 문자열로 표시하려면 실제 값이 필요하다.

```python
x = mx.ones((4,))
print(x)
values = x.tolist()
scalar = mx.sum(x).item()
```

디버깅 출력이나 `item()`도 실행 경계가 된다. 모델의 반복문 안에서 매 단계 손실 값을 Python 숫자로 바꾸면 계산을 자주 기다릴 수 있다. 로그 빈도를 조정하는 것만으로도 성능이 바뀔 수 있는 이유다.

shape나 dtype 같은 메타데이터를 읽는 것과 모든 숫자 데이터를 읽는 일은 구분한다. 필요한 정보가 메타데이터뿐이라면 불필요하게 결과 전체를 변환하지 않는다.

## 사용하지 않는 출력과 그래프 수명

```python
x = mx.arange(4, dtype=mx.float32).reshape(2, 2)

def two_outputs(x):
    total = mx.sum(x)
    product = x @ x
    return total, product

total, product = two_outputs(x)
mx.eval(total)
```

`total`만 평가하면 그 출력의 의존 관계에 없는 `product`의 행렬곱 결과까지 요구하지 않는다. 그러나 함수가 호출되면서 해당 노드는 이미 구성됐고 Python 참조도 남을 수 있다.

‘평가하지 않았으니 비용이 전혀 없다’는 결론은 틀리다. 그래프 구성과 참조 관리 비용이 있고, 반복문에서 노드를 계속 연결하면 그래프가 커질 수 있다. 필요 없는 출력에 대한 참조를 오래 보관하는지도 확인한다.

## 재현 가능한 벤치마크 설계

공유한 [재현 스크립트]({{ '/assets/examples/mlx/reproduce.py' | relative_url }})는 다음 조건을 고정한다.

| 항목 | 설정 |
| --- | --- |
| 입력 | 512×512 행렬 두 개 |
| 자료형 | float32 |
| 환경 | Apple M4, macOS 15.6, Python 3.12.16 |
| 패키지 | MLX 0.32.4 |
| 워밍업 | 장치별 3회 |
| 측정 | 장치별 12회 |
| 완료 경계 | 매 표본에서 새 결과를 만들고 `mx.eval` |
| 입력 생성 | 측정 시작 전에 평가 완료 |

아래는 스크립트의 핵심 흐름이다. `time`을 import하고 `a`, `b`를 먼저 만든 뒤 평가한 상태에서 측정한다. 전체 스크립트는 CPU·GPU별 스트림도 설정한다.

```python
start = time.perf_counter()
out = a @ b
constructed = time.perf_counter()
mx.eval(out)
finished = time.perf_counter()

graph_ms = (constructed - start) * 1000
completion_ms = (finished - constructed) * 1000
total_ms = (finished - start) * 1000
```

`graph_ms`는 Python 호출과 결과 그래프 구성 구간이다. `completion_ms`는 이후 평가·스케줄링·완료 대기 구간을 포함한다. 두 번째 값만으로 순수 GPU 커널 실행 시간을 얻었다고 해석하면 안 된다.

같은 입력 배열을 재사용하더라도 매 표본에서 `a @ b`로 새로운 결과를 만든다. 이미 평가된 결과에 `eval`만 반복하면 새 행렬곱을 측정하지 못한다.

## 실제 측정 결과와 해석

2026년 11월 19일 재현 스크립트를 실행한 한 번의 결과다. 반올림한 값이며 성능 보증 수치가 아니다.

| 장치 | 그래프 구성 중앙값 | 전체 중앙값 | 전체 p95 |
| --- | ---: | ---: | ---: |
| CPU | 0.0006 ms | 0.1735 ms | 0.1855 ms |
| GPU | 0.0006 ms | 0.5506 ms | 0.9641 ms |

이 입력과 측정 조건에서는 CPU가 더 빨랐다. 이 행렬곱은 출력 원소가 512²개이고 원소마다 길이 512의 내적을 계산하므로 약 `2 × 512³ = 268,435,456`회의 부동소수점 연산으로 셀 수 있다. 곱과 덧셈을 각각 한 번으로 센 계산량이며 실제 명령 수나 처리량을 측정한 값은 아니다. 작은 작업은 GPU 연산 능력을 충분히 활용하기 전에 제출·스케줄링·완료 대기 비용의 영향을 크게 받을 수 있다. 이는 가능한 설명이며, 이 측정만으로 병목 비중을 정량 분해한 것은 아니다.

표본은 12개이므로 p95는 가장 느린 표본에 해당한다. 안정적인 지연 분포를 연구하려면 표본 수를 늘리고 독립된 실행을 반복해야 한다. 입력 크기, dtype, 전원·열 상태, 다른 프로세스 부하도 함께 기록한다.

### 이 결과로 주장할 수 없는 것

- 모든 행렬곱에서 CPU가 더 빠르다는 결론
- 다른 모델이나 다른 Apple 칩에서도 같은 비율이라는 결론
- GPU 커널 자체가 0.5506 ms 걸렸다는 결론
- 입력 생성·파일 읽기·전처리까지 포함한 제품 지연이라는 결론

더 큰 행렬, 배치 크기 변화, 실제 모델 층을 별도로 측정해야 한다. GPU 성능을 논할 때 작은 단일 연산과 충분히 큰 계산을 구분하는 것이 중요하다.

## 캐시된 결과를 다시 평가하는 시간

같은 측정에서 이미 계산한 마지막 출력을 다시 `eval`한 시간은 CPU 경로에서 약 0.0012 ms, GPU 경로에서 약 0.0008 ms였다. 이 값은 행렬곱을 다시 실행한 시간이 아니다.

평가 함수 호출, 상태 검사와 필요한 대기 같은 비용이 남을 수 있으므로 ‘두 번째 eval은 아무 일도 하지 않는다’보다 ‘같은 결과의 계산을 다시 수행하지 않는다’고 설명하는 편이 정확하다.

## 메모리 지표가 의미하는 범위

`mx.get_active_memory()`는 MLX allocator의 활성 메모리를 관찰하는 지표다. 프로세스 전체의 메모리 사용량이나 그래프의 Python 객체 크기 전체를 대표하지 않는다.

스크립트에서 1024×1024 float32 배열을 구성하고 평가했을 때 다음 값이 관찰됐다.

| 시점 | 활성 메모리 |
| --- | ---: |
| 구성 전 | 8 bytes |
| 그래프 구성 후 | 12 bytes |
| 평가 후 | 4,194,316 bytes |
| 배열의 논리적 크기 | 4,194,304 bytes |

출력 데이터 버퍼가 평가 시점에 나타나는 흐름은 볼 수 있다. 하지만 숫자가 작다고 전체 시스템이 그만큼의 메모리만 사용한 것은 아니다. 그래프 메타데이터, Python 런타임, 캐시와 이미 존재한 배열 등은 별도로 고려한다.

캐시된 메모리와 활성 메모리, 피크 사용량은 구분해서 해석한다. 반복 실험 전에 무조건 캐시를 비우면 실제 제품과 다른 cold-start 조건을 측정할 수도 있다.

## 지연 평가와 컴파일은 다른 기능이다

지연 평가는 언제 값을 계산할지에 관한 실행 방식이다. `mx.compile`은 함수의 계산을 최적화하는 별도 변환이다. 지연 계산을 썼다는 이유만으로 모든 연산이 하나의 커널로 융합된다고 가정하면 안 된다.

배열 하나를 구성했다는 사실은 `mx.compile`을 호출했다는 뜻도 아니다. 컴파일 성능을 비교하려면 첫 호출 비용과 반복 실행을 분리하고, 입력 shape·dtype 변화에 따른 동작도 확인한다. 순수 Python 부수 효과나 외부 상태에 의존하는 함수는 컴파일 경계에서 별도로 검토해야 한다.

## 제품 코드에서의 평가 경계

학습 루프에서는 손실과 갱신된 파라미터 등 필요한 상태를 적절한 주기로 평가한다. 너무 자주 기다리면 작업 준비 비용이 늘고, 지나치게 미루면 그래프와 임시 상태가 커질 수 있다.

작은 실제 구현은 [MLX 자동 미분과 학습 루프]({{ '/ai/mlx/training-loop/' | relative_url }})에서 확인할 수 있다. 그 예제는 매 단계 갱신한 파라미터를 평가하고, 기록할 때만 Python 스칼라로 손실을 꺼낸다. ‘갱신 전 손실’과 ‘갱신 후 손실’도 구분해 기록한다.

언어 모델의 추론(학습된 모델로 결과를 만드는 것)에서는 첫 토큰(모델이 글을 처리하는 단위)이 나오기까지의 지연, 이후 토큰 생성 속도, 여러 요청을 묶어 처리하는 배치 처리량이 서로 다른 지표다. 행렬곱 한 번의 시간을 전체 언어 모델의 성능으로 대체하지 않는다.

실제로 어느 경계가 적합한지는 작업 규모와 메모리 제약을 함께 측정해 결정한다. 이 글의 작은 벤치마크는 측정 방법을 설명하는 출발점이다.

## 주요 API

| API | 역할 |
| --- | --- |
| `mx.eval(*arrays)` | 그래프를 평가하고 결과가 준비될 때까지 기다린다 |
| `mx.async_eval(*arrays)` | 평가를 예약만 하고 바로 돌아온다 |
| `mx.synchronize()` | 예약된 작업이 끝날 때까지 기다린다 |
| `mx.compile(fn)` | 함수의 계산 그래프를 최적화한 함수로 바꾼다. 지연 평가와는 별개 기능 |
| `mx.ones(shape)`, `mx.arange(n)` | 측정용 입력 배열 생성 |
| `a.item()`, `print(a)`, `np.array(a)` | 값을 꺼내는 순간 평가가 일어난다 |
